# 05 让项目学习，并改善代码拓扑

一个 Case 关闭了，不代表它产生的所有内容都该进入长期知识库。

这章先完成记忆循环的最后一步：用 Weave 把已验证的新事实写回。然后再解释，为什么上下文解耦与 AI 友好代码拓扑是建立在这个循环之上的进阶方向。

## 先区分结果、过程和候选

一次 Case 可能包含：

- 调研中看过的外部资料。
- 被否决的方案。
- 最终采用的产品规则。
- 为了调试临时加的日志。
- 新增页面的数据流和入口。
- 未来可能想做但本次没做的能力。

把它们全部塞进 `_aipd/knowledge` 会让长期知识迅速变脏。AIPD 的原则是：

- 一次性过程留在 Case / Work Package。
- 未实现设计和未来计划留在 Case，不能写成当前事实。
- 已经完成、实现或验证的稳定信息，才进入 Weave 判断。

## Weave 怎样决定写到哪里

```text
新信息
├── 项目长期方向是否改变？        -> Intent（需用户确认）
├── 是否是带来源的外部事实？      -> Research
├── 项目靠什么成立？            -> Core
├── 用户会看到什么规则？        -> Product
├── 多个入口要遵守什么实现约定？ -> Engineering
├── 只影响一个页面或组件？       -> 就近 README
├── 下一次怎样更快命中？         -> map
└── 只属于这次执行？             -> Case / Work Package
```

例如退款 Case 完成后：

- “本项目不提供人工代办退款”经用户确认后可能进入 Intent。
- 某支付渠道最新退款时限及来源可能进入 Research。
- “发货状态和退款资格的关系”可能进入 Core。
- “已发货订单不可自助退款，用户看到什么提示”可能进入 Product。
- “前后端都必须以服务端资格判定为准”可能进入 Engineering。
- 退款弹窗的组件和数据流进入页面 README。
- “退款”“已发货”到上述入口的关键词映射进入 map。

Weave 不是自动分类器。它要检查新事实是否真的稳定、是否与旧认知冲突、哪个位置是知识 owner，并避免复制多份完整定义。

## Weave、Learn、Inbox 和 Update 不同

| 能力 | 处理什么 | 不处理什么 |
|---|---|---|
| Inbox | 未整理、低承诺度的信息 | 不自动当成长期事实或待办 |
| Weave | 当前项目已完成、已验证的新知识 | 不做聊天存档，不更新 AIPD 框架本身 |
| Learn | 从 transcript、Case 或用户反馈更新 AIPD 框架经验 | 不替代当前项目 Weave |
| Update | 把新版 AIPD 结构安全合并进已初始化项目 | 不覆盖项目已有认知 |

这四个入口共同控制“什么现在先放着、什么已经可以留下、框架本身怎样进化”。

## 为什么循环跑起来后，代码拓扑也会变化

当 Agent 经常执行局部任务时，一个新成本会变得明显：理解一次改动需要跳多少上下文，以及改一个共享点会牵出多少隐含调用方。

传统工程常把消除重复放在很高优先级。对 Agent 来说，过早抽成共享 helper、service 或全局状态，可能让一个局部需求必须跨很多文件和语义边界才能读懂。

AIPD 因此使用“上下文解耦”判断理解边界，并把它投影为更具体的代码拓扑：

- **横向基座**：路由、部署、日志、鉴权等多个业务共同需要的技术地基。
- **横向共享能力**：已有多个真实使用者、语义和输入输出稳定、可独立验证的能力。
- **纵向业务上下文**：围绕一个业务目标，把输入、规则、状态、输出和局部实现收在有限上下文内。
- **显式组合边界**：让它们通过稳定输入、输出、事件或协议连接，而不是互相穿透内部状态。

页面、接口、组件或业务模块不因为名字就自动属于哪一类。真正的判断是：Agent 能否在有限上下文内读清目标和验收，外部是否只依赖稳定入口，修改时是否能控制无关牵连。

## Decouple first, DRY later

重复逻辑不能只凭代码相似、调用次数或假想需求上移 shared。更稳的顺序是先让能力在局部上下文中独立成立，再确认：

- 已有多个真实使用者依赖同一语义。
- 输入输出小而明确。
- 抽取会减少理解跳转和牵连面。
- 有 owner、测试或替换边界可以验证影响。

它的优先级是：

> 先降低牵连面，再控制代码量，最后判断抽象。
> Decouple first, DRY later.

语义仍会分叉时，可以暂时保留局部重复。复制是阶段性保护手段，不是永久目标。

## Case 怎样承接拓扑判断

结构性开发命中代码拓扑条件时：

- Design 读取通用指南，写成项目具体的 `Code Topology Contract`。
- Execute 的拓扑敏感 Work Package 只带当前目标所需的短护栏；需要改合同就回 Design。
- Verify 对照真实 diff、目录、依赖、测试和文档回写审计，不只检查“代码能运行”。

普通字段修改、样式修复、明确上下文内的 bugfix 和纯文档整理通常不加载这套指南。

## 这不是必须采用的代码规范

上下文解耦和代码拓扑是 AIPD 的进阶判断，不是安装后必须重构整个项目的教条，也不要求项目全面纵向化。

它适合在真实问题出现时渐进采用：

- 一个页面每次修改都要跨十几个目录。
- 一个共享 helper 的隐含语义越来越多。
- 多个 Agent 经常因为边界不清修改同一主干。
- 局部模块难以独立验收和替换。

如果当前代码结构已经清楚、牵连可控，就没有必要为了“AIPD 风格”重写。更完整的原理见[上下文解耦](../modules/context-decoupling.md)，模块、shared 和 Case 合同判断见 [AI 友好代码拓扑](../modules/ai-friendly-code-topology.md)，可运行的 Vue3 经验源码位于仓库根级 `experience-assets/`。
