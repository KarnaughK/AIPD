# AI 友好代码拓扑

当你要新增模块、重划文件夹边界、抽取 shared、改变跨模块依赖，或一个局部需求总要跳过很多文件才能理解时查这篇。

AI 友好代码拓扑是一套边界判断，不是固定目录模板，也不要求把项目“全面纵向化”。现有项目的 Map、Engineering、局部 README 和真实代码事实始终优先。

## 先区分两个命名空间

“横向 / 纵向”在这里专指真实代码拓扑：

- 代码拓扑：横向基座、横向共享能力、纵向业务上下文。
- AIPD Workspace：Intent / Research / Core / Product / Engineering 五类并列知识，以及 Map、SOP、Case 等独立能力。

五类 Knowledge 不是代码纵向层级；多个彼此独立的业务模块称为并列扩展，也不自动等于横向共享。

## 三类模块和一种连接

| 类型 | 负责什么 | 常见例子 |
|---|---|---|
| 横向基座 | 多个业务上下文共同需要、但不拥有具体业务需求的技术地基 | 路由、部署、日志、鉴权、数据访问适配、站点壳 |
| 横向共享能力 | 已被多个真实业务上下文使用，语义、输入输出和 owner 稳定的能力 | 成熟的上传、搜索参数协议、通用运行机制 |
| 纵向业务上下文 | 围绕一个业务目标，把输入、规则、状态、输出和局部实现收在有限上下文内 | 页面、业务弹框、API 链路、网站或游戏功能 |
| 显式组合边界 | 让上述模块连接的稳定输入、输出、事件或协议 | public API、事件、命令、结果对象 |

显式组合边界是连接方式，不是第四类模块。外部应依赖稳定入口，不穿透另一个上下文的私有 service、store、组件或中间状态。

## 怎样识别纵向业务上下文

目录名、文件长度和技术栈不能自动决定边界。优先检查：

- 它是否围绕一个清楚的业务目标，而不是只按 controller / service / model 等技术职责分类。
- Agent 能否在有限局部上下文内读清输入、规则、状态、输出和验收。
- 它能否独立修改、验证和演进，而不必审计大量无关调用方。
- 外部是否只依赖稳定入口。

`纵向` 描述业务归属和演进方向；`黑箱` 描述边界质量。横向基座和共享能力同样需要清楚的黑箱边界。

## Shared 什么时候才值得上移

AIPD 使用 `Decouple first, DRY later`：先让能力在局部上下文中独立成立，再观察是否值得晋升为横向共享。

不能只凭代码相似、调用次数或假想需求抽取 shared。上移前至少确认：

- 已有多个真实使用者，并依赖同一稳定语义。
- 输入输出小而明确，调用方不必理解内部状态。
- 抽取能减少理解跳转和牵连面，而不是制造新的全局依赖网。
- 有独立 owner、测试或替换边界，变更影响可验证。

业务语义仍可能分叉，或抽取后需要大量模式参数与交叉状态时，可以暂时保留局部重复。复制是阶段性保护手段，不是永久目标。

## Brownfield 的最小改法

调整现有项目时：

1. 先从项目 Map、Engineering、局部 README 和代码确认当前 owner。
2. 判断本次目标属于哪个纵向业务上下文。
3. 列出允许使用的现有横向基座与共享能力。
4. 检查新增引用是稳定组合，还是穿透其他模块内部。
5. 未在 Design 中明确批准时，默认不新增共享层。
6. 只做目标所需的最小 delta，不把局部任务变成全局拓扑重构。
7. 明确当前上下文怎样独立验收，以及稳定结果写回哪里。

## 在 Case 中怎样落地

代码拓扑不是 Execute 临场发挥的风格偏好。命中结构性改动时，Case 会在三个阶段使用不同粒度的合同：

- **Design**：读取通用指南，形成项目具体的 `Code Topology Contract`，写清业务上下文、允许的横向依赖、显式组合、禁止穿透、shared 权限和独立验收。
- **Execute**：拓扑敏感 Work Package 只携带当前目标所需的短护栏；实现需要改变合同就回 Design。
- **Verify**：对照真实 diff、目录、依赖、测试和文档回写审计合同，不只检查代码能否运行。

局部字段修改、样式修复、明确上下文内的 bugfix 和纯文档整理通常不加载这套指南。

## 与上下文解耦的关系

[上下文解耦](context-decoupling.md)解释为什么 AI 执行更在意局部自足、上下文跳转和牵连面；本页把这套判断投影到真实代码模块与依赖关系。

因此它不反对已经成立的横向基座，也不为“纵向纯度”拒绝成熟 shared。目标是让每个边界更容易独立理解、修改、替换和验证。
