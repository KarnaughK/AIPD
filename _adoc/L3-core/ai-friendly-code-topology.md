# AI 友好代码拓扑

AI 友好代码拓扑是 AIPD“AI 原生代码架构模型”中的一项具体判断。它回答：当 AI 深度参与开发时，代码如何组织，才能让局部任务更容易被完整读取、独立修改、验证和替换。

它是一套边界决策模型，不是固定目录模板，也不是要求项目“全面纵向”。项目通常同时存在横向基座、横向共享能力和纵向业务上下文；真正要控制的是隐性依赖、理解跳转和改动牵连面。

## 先区分两个命名空间

AIPD 目前在两个不同问题中都会使用“横向 / 纵向”，不能混写：

| 命名空间 | 纵向 | 横向 | 回答的问题 |
|---|---|---|---|
| 代码拓扑 | 纵向业务上下文 | 横向基座、横向共享能力 | 真实代码如何按业务归属、依赖和演进边界组织 |
| AIPD 知识与流程系统 | 纵向概念模块 | 横向功能能力 | 项目认知放在哪一层，以及 Agent 做事时如何串起这些层 |

`纵向概念模块 / 横向功能能力` 详见 `_adoc/L3-core/vertical-concept-modules.md` 和 `_adoc/L3-core/horizontal-capabilities.md`。本文只讨论代码拓扑。

新增多个独立业务模块时，统一称为 **并列扩展**，不称“横向铺模块”。“横向”在代码拓扑中专指跨业务上下文的基座或共享能力。

## 核心模型

```text
横向基座 ───────────┐
                    ├─ 支撑 / 服务多个纵向业务上下文
横向共享能力 ───────┘

纵向业务上下文 A    纵向业务上下文 B    纵向业务上下文 C
       └──────── 通过显式组合边界连接 ────────┘
```

前三者是模块类型；显式组合边界是模块之间的连接方式，不是第四类模块。

### 横向基座

横向基座承接多个业务上下文都需要、但不拥有某个具体业务需求的基础能力。例如：

- 路由注册、部署、日志、埋点、鉴权和数据访问适配。
- 站点壳、运行时、SEO 基础设施和统一观测机制。
- 已经稳定的表单、列表、弹框等页面运行机制。

基座的职责是提供技术地基和稳定机制，不能吸收具体业务上下文的关键词内容、业务分支、局部状态或演进节奏。基座同样需要明确 owner、契约和边界；“多个模块以后可能会用”不足以支撑预建一个大平台。

### 横向共享能力

横向共享能力是被多个纵向业务上下文真实使用、语义已经稳定、拥有清楚契约的技术或业务能力。

它和横向基座的差别主要在形成路径：基座通常作为项目运行所需的公共地基存在；共享能力往往先在一个或多个纵向上下文中成立，经过实践后再向上沉淀。

共享不能只由代码相似、调用次数或“重复三次”触发。抽取以后如果要求所有调用方理解内部状态，或让一次局部修改变成全局影响分析，它就不是 AI 友好的共享。

### 纵向业务上下文

纵向业务上下文面向一个可独立理解、修改、验证和演进的业务目标，尽量把相关输入、规则、状态、输出和局部实现收在同一上下文中。

它的粒度不由固定文件夹名称决定。页面、业务弹框、独立域名网站、具体 SEO 页面、游戏、API 业务链路，都可能成为纵向业务上下文。判断时优先问：

- 它是否围绕一个清楚的业务目标，而不是只按技术职责归类。
- Agent 修改它时，能否在有限局部上下文内读清输入、规则、状态、输出和验收条件。
- 它能否独立变化和验证，而不要求同时审计大量无关调用方。
- 它的内部实现是否主要归它自己所有，外部只依赖稳定入口。

因此，纵向业务上下文既可能是一个文件，也可能是一个文件夹、一组文件或更大的子项目。固定 token 数、固定目录层级和固定技术名词都不是判定标准。

## “纵向”和“黑箱”不是同一个属性

`纵向` 描述模块的业务归属和演进方向；`黑箱` 描述模块边界是否清楚、外部是否只依赖稳定契约。

纵向业务上下文应尽量形成黑箱，但横向基座和横向共享能力也必须有黑箱边界。反过来，一个按页面或 API 文件夹组织的模块，如果外部仍然穿透它的 store、service 和内部状态，就只是物理上放在一起，并没有形成可用黑箱。

因此，本文优先使用“纵向业务上下文”描述模块类型，使用“黑箱边界”描述模块质量，不再用“纵向黑箱”代指整个项目架构。

## 嵌套与显式组合

纵向业务上下文不等于完全无引用。一个网站内部可以继续包含更小的纵向页面或弹框；一个 SEO 页面可以通过稳定入口嵌入一个独立游戏；一个页面也可以组合横向表单机制和纵向业务弹框。

允许的关系是显式组合：

- 调用方只依赖小而稳定的输入、输出、事件或协议。
- 被组合模块拥有自己的状态、规则、生命周期和内部实现。
- 调用方不穿透边界直接读取或操纵内部 service、store、私有组件或中间状态。
- 替换被组合模块时，调用方不需要重写自己的业务主干。

如果两个模块必须互相知道大量内部细节，应先检查边界是否切错，而不是继续增加隐式引用或用共享状态把它们粘在一起。

## 复制与共享的晋升顺序

“Decouple first, DRY later”描述的是共享能力的晋升顺序，不是“永久不要共享”：

```text
先在纵向业务上下文中独立成立
            ↓
观察多个上下文是否出现稳定共同语义
            ↓
满足上移条件后，沉淀为横向共享能力
```

在业务语义仍可能分叉、共享后需要大量模式参数或交叉状态时，复制完整局部实现往往比过早复用更容易理解和修改。复制不是目标，而是保护独立演进边界的阶段性手段。

一项能力晋升为横向共享能力前，至少应满足：

- 已有多个真实使用者，不是为了假想需求预建。
- 使用者依赖的是同一稳定语义，不只是当前代码形状相似。
- 能通过小而清楚的输入输出使用，不要求调用方理解内部状态。
- 抽取后会减少理解跳转或牵连面，而不是制造新的全局依赖网。
- 拥有独立 owner、测试或替换边界，变更影响可以被验证。

如果这些条件不成立，优先让各纵向上下文分别演进；如果条件已经成立，则应共享，不应为了形式上的“纵向纯度”继续复制。

## 常见形态

| 场景 | 横向部分 | 纵向业务上下文 | 组合边界 |
|---|---|---|---|
| 业务前端 | 表单、列表、分页、全局弹框运行机制 | 具体页面、业务弹框、局部组件 | props、events、表单值与提交结果 |
| 多站点工作空间 | 部署、观测、后台管理、统一站点壳 | 每个独立域名网站；站内还可继续拆页面上下文 | 站点配置、公共服务接口、引流协议 |
| SEO 主题游戏站 | 路由、SEO、布局、埋点和页面模板骨架 | 具体关键词页面、具体游戏模块 | 游戏挂载参数、结果事件、展示槽位 |
| API 服务 | 鉴权、日志、数据库适配、通用协议 | 某个 API 对应的完整业务链路 | 请求 / 响应契约、领域事件、稳定服务接口 |

这些形态用于帮助识别边界，不代表所有项目必须采用相同目录结构。页面模板骨架可以是横向能力，但针对具体关键词形成的页面仍属于纵向业务上下文；通用弹框引擎可以横向共享，携带具体业务状态和生命周期的弹框仍可以纵向独立。

## 在具体项目中的落点

AIPD 全局只提供判断模型，不替具体项目预先决定模块清单。实际落地时：

1. Case Design 在 `02-design/context-boundary.md` 或 Design 主文档中识别现有横向基座、横向共享能力、纵向业务上下文和显式组合边界。
2. 实现稳定后，跨多个代码入口的项目级拓扑与工程规则回写项目 `_adoc/L5-dev/`。
3. 页面、弹框、游戏、网站、API context 内部的入口、数据流和修改注意事项写到代码就近 `README.md`。
4. 项目 `_adoc/map.md` 只负责把用户说法路由到 L3 / L4 / L5 / 局部 README / L6，不复制完整拓扑正文。

Agent 在设计或修改代码前，应最少检查：

- 当前业务目标对应哪个纵向业务上下文。
- 它依赖哪些现有横向基座和已经成立的共享能力。
- 新引用属于稳定组合，还是穿透了另一个模块的内部实现。
- 新 shared 是否满足真实使用者、稳定语义和降低牵连面的晋升条件。
- 完成后能否对当前上下文独立理解、修改和验收。

## 外部 Agent 的运行时投影

本文件是 AIPD 长期抽象认知的主事实源。安装后的外部 Agent 不依赖本仓库 `_adoc`，而是按任务条件读取：

- 运行时投影 owner：`aipd-skill/src/core/ai-friendly-code-topology.md`。
- 普通结构性开发入口：`aipd-skill/src/skills/aipd/SKILL.md`。
- 正式 Case 入口：`aipd-skill/src/skills/aipd-case/SKILL.md`，由 Design 形成项目具体合同，Execute 执行短护栏，Verify 审计真实结果。

运行时投影从本文提炼判断合同，不逐字复制案例证据和 AIPD 仓库归属说明。两者的 owner 与构建验证边界见 `_adoc/L5-dev/index.md`。

## 非目标与边界

- 不要求项目全面纵向，也不反对横向基座和真实共享能力。
- 不提供跨技术栈统一的目录模板；目录只是边界的一种物理表达。
- 不规定所有页面、API、组件或网站天然就是纵向业务上下文。
- 不用文件长度、token 数、重复次数或调用数量自动决定拆分与共享。
- 不把“局部复制”升级为永久规则；语义稳定并满足晋升条件后应考虑共享。
- 不预建无真实使用面的巨大横向平台；横向模块也必须保持可理解、可测试和可替换。
- 不把代码拓扑的纵横术语套到 AIPD 知识与流程系统，反之亦然。

当前模型仍属于 AIPD 的 AI 原生代码架构探索。它提供长期判断和设计检查项，但具体技术栈中的有效边界仍应通过真实项目、实现验证和后续经验回写持续校准。
