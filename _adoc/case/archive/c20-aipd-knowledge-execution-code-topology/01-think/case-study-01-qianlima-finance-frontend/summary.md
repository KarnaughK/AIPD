# 案例 01：千里马外包财务系统

## 案例信息

- **时间顺序**：AIPD 发展过程中的第一个项目案例。
- **项目**：为“千里马”交付的外包财务系统。
- **技术形态**：纯前端后台管理项目。
- **证据来源**：用户 2026-08-09 对当时架构与取舍的回忆说明。
- **采集状态**：已保存；尚未与其他案例比较。

## Branch Goal

忠实记录这个纯前端项目中已经出现的横向能力与纵向模块，以及复制、共享、页面独立和弹框边界的实际取舍。当前不将它推广为 AIPD 通用规则。

## 横向能力：通用框架

用户当时将脱离单一页面、可服务多个页面的通用能力抽成横向框架，主要包括：

1. **表单页框架**。
2. **列表页页面逻辑框架**：处理筛选项取值和传递、分页传递、数据保存及事件传递。
3. **“复杂表达与分页功能”**：按用户原话暂存；其中“复杂表达”的具体含义尚未校准，不在采集阶段自行改写。
4. **全局弹框框架**。

这些横向能力不是某个具体业务页面，而是承载多个页面共同机制的基础。

## 纵向模块：页面与局部组件

### 页面是主要纵向模块

- 每个页面作为一个大的纵向模块。
- 不同页面尽量保持独立，不互相连通。
- 页面自己管理属于该页面的展示、状态和业务变化。

### 相似 List Item 也不跨页面共享

- 即使两个页面出现相同或相似的 List Item，例如同一种“物品 Item”同时出现在两个列表中，也不会自动抽成共享组件。
- 用户宁愿复制两份列表或 Item，让两个页面分别管理。
- 后续修改各改各的，避免一个共享组件逐渐混入多个页面的状态与分支。

### 小型纵向组件

- 页面内部偶尔还会出现较小的纵向组件。
- 弹框是典型特例：它既可以留在页面内部，也可以抽到页面之外。
- 与只负责一小段展示的 List Item 相比，弹框更像完整模块，因为它拥有自己的打开、关闭和生命周期。

## 三种任务形态、三个独立弹框

用户提供的具体例子：

- 一个任务对象存在三种形态。
- 修改三种形态时分别出现三个弹框。
- 三个弹框大约一半相同，另一半各自不同。
- 最终没有做成一个包含大量模式与状态判断的统一弹框，而是创建三个彼此无关的弹框。
- 实现时可以先完成一个，再复制成另外两个；复制完成后，它们各自演进。

后续修改时宁愿修改三套，也不把三种形态重新塞回一套复杂状态管理中。

## 当时的取舍理由

- 接受局部代码重复，以换取页面和弹框的独立性。
- 降低共享组件内部的状态分支数量。
- 缩小单次修改的牵连范围。
- 让代码结构更直接，降低后续阅读和理解难度。
- 避免“为了复用相同的一半”而把“不相同的另一半”耦合起来。

## 用户对当时认知的重新观察

用户最初曾把方向想象成“完全纵向”：不再建一栋不断向上叠加的摩天大楼，而是在地面无限铺开一片独立别墅，以大量纵向模块承载原有系统规模。

现在回看，这个第一个项目其实从一开始就已经不是全面纵向，而是：

```text
横向地基 / 通用框架
        ↓
纵向页面与完整局部组件
```

这里的“横向地基 + 纵向产物”只是案例内观察，尚未上升为跨项目结论。
