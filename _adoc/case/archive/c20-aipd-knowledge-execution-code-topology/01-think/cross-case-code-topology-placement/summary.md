因此，本轮可以形成方向性代码拓扑模型，但仍应标为 AI 原生代码架构探索，不应包装成所有技术栈必须照抄的目录规范。

## 跨案例共同结论

### 1. 项目不应被描述为“全面纵向”

三个案例都存在横向结构。差别只在横向结构的具体内容：

- 页面框架、表单控制、列表控制和全局弹框机制。
- 多站观测、后台管理、部署接入和公共服务。
- 路由、SEO、布局、埋点、运行时和页面嵌入协议。

纵向化解决的是业务上下文如何独立演进，不是否定项目级基础设施、稳定公共机制和真实共享能力。

### 2. 代码拓扑至少包含三类模块

#### 横向基座

承接多个业务上下文都必须依赖、且不拥有某个具体业务需求的基础能力，例如：

- 路由注册、部署、日志、埋点、鉴权和数据访问适配。
- 表单、列表、弹框等经过验证的页面机制。
- SEO、语言、站点壳和运行时基础设施。

横向基座的价值是减少每个纵向模块重复建设技术地基，但它不能吸收纵向模块的关键词内容、业务分支和局部状态。

#### 横向共享能力

已经被多个纵向上下文真实使用、语义稳定、拥有清楚契约的业务或技术能力。它与基座的区别是：基座通常先于具体业务存在，共享能力往往从多个纵向实践中后置沉淀。

共享不能只由代码相似或调用次数触发。上移后至少应满足：

- 共享的是同一稳定语义，而不只是当前代码形状相似。
- 能通过小而清楚的输入输出使用，不要求调用方理解内部状态。
- 抽取后减少理解跳转或牵连面，而不是制造新的全局依赖网。
- 有独立 owner、测试或替换边界。

#### 纵向业务上下文

面向一个可独立理解、修改、验证和演进的业务目标，尽量把输入、规则、状态、输出和局部实现放在同一上下文中。

纵向业务上下文的粒度不是固定目录级别。三个案例分别出现：

- 页面、弹框。
- 独立域名网站。
- 具体 SEO 页面、具体游戏模块。

判断标准是独立变化和验收边界，而不是“页面 / API / 文件夹”这些固定名词。

### 3. 纵向盒子可以嵌套，也可以组合

纵向黑箱不等于完全无引用。Guessword.io 表明：一个纵向页面可以通过稳定入口嵌入一个纵向游戏模块；Page One 的网站内部也可能继续出现更小的纵向模块。

允许的关系是显式组合：

- 调用方只依赖稳定输入输出。
- 被组合模块仍拥有自己的内部状态和规则。
- 调用方不穿透边界读取内部 service、store 或状态细节。

因此，“组合关系”不是第四类模块，而是纵向模块之间或横向能力与纵向模块之间的显式连接方式。

### 4. 复制与共享是阶段判断，不是二选一教条

案例 01 证明，在业务语义尚会分叉、共享后需要大量模式状态时，复制完整模块可以降低整体理解成本。案例 02、03 又说明项目仍需要真实公共能力。

更准确的顺序是：

```text
先在纵向上下文中独立成立
        ↓
观察多个上下文是否形成稳定共同语义
        ↓
满足上移条件后进入横向共享能力
```

“Decouple first, DRY later”仍成立，但它现在应被解释为共享能力的晋升顺序，而不是“永久不要横向能力”。

## 不能从三个案例推出什么

- 不能推出所有项目都使用同一目录结构。
- 不能推出所有页面、API、组件或网站天然就是纵向黑箱。
- 不能推出业务模块永远不能共享。
- 不能用“重复三次”或调用数量作为自动抽取规则。
- 不能把 Page One 的 platform 和 Guessword.io 的多游戏拓扑写成已经完成验证的实践经验。
- 不能把横向基座预建成无边界的大平台；横向层同样需要 owner、边界和真实使用面。

## 术语收口

建议把整套模型命名为 **AI 友好代码拓扑**，作为 AIPD “AI 原生代码架构模型”中的一个具体模型。

| 使用场景 | 建议术语 | 避免的说法 |
|---|---|---|
| 整个代码组织模型 | AI 友好代码拓扑 | 纵向架构 / 全面纵向 |
| 跨业务基础设施 | 横向基座 | 所有 shared 都叫基座 |
| 后置沉淀的稳定复用 | 横向共享能力 | 相同代码自动抽象 |
| 独立业务上下文 | 纵向业务上下文 / 纵向业务模块 | 所有文件夹都叫纵向黑箱 |
| 多个纵向模块继续增加 | 并列扩展 | 横向铺模块 |
| 纵向模块之间的调用 | 显式组合边界 | 模块间完全不能引用 |
| AIPD 知识系统结构 | 纵向概念模块 / 横向功能能力 | 与代码纵横术语混写 |

其中最关键的校正是：`横向铺模块` 过去只是空间比喻，但现在会和“横向基座 / 横向共享能力”冲突。后续应改成“并列增加纵向业务模块”或简称“并列扩展”。

## 推荐落点

### 主事实源

新建：

```text
_adoc/L3-core/ai-friendly-code-topology.md
```

它属于现有“AI 原生代码架构模型”，不新增第九个 L3 成立模型。正文负责：

- 区分代码拓扑与 AIPD 知识系统的纵横术语。
- 定义横向基座、横向共享能力、纵向业务上下文。
- 解释嵌套、组合、复制与共享晋升条件。
- 明确这是决策模型，不是固定目录模板。
- 保留案例证据强弱，不把规划写成已验证事实。

`_adoc/L3-core/index.md`、`_adoc/L3-core/map.md` 和项目 `_adoc/map.md` 只放摘要与直接入口。

### Agent 执行投影

更新 `aipd-skill/src/core/case/phases/design.md` 的 Context Decoupling & File Boundary Design：

1. 先识别横向基座、现有横向共享能力和纵向业务上下文。
2. 检查纵向模块是否能独立理解、修改和验收。
3. 区分显式组合与穿透内部实现。
4. 对新 shared 写明真实使用者、稳定语义和上移收益。
5. 把“横向铺模块”改为“并列扩展纵向模块”。

必要时同步 case 模板中的 `context-boundary.md` 提示，但不把完整哲学复制进模板。

### 面向用户的解释

更新 `docs/modules/context-decoupling.md`：

- 把“从横向分层到纵向黑箱”改成“横向基座与纵向业务上下文”。
- 明确不是全面纵向，也不是反 shared。
- 用三个短案例形状解释不同粒度，但注明设计证据与已验证实践的区别。

L1 Intent 只需把“更关注纵向黑箱”修成“让横向基座与纵向业务上下文按不同规则演进”，避免顶层方向继续给人全面纵向的印象。

### 具体项目如何落地

AIPD 只提供判断模型。某个项目最终有哪些横向和纵向模块，应在 Case Design 先写入 `02-design/context-boundary.md`；实现稳定后：

- 跨多个代码入口的项目级拓扑回写项目 `_adoc/L5-dev/`。
- 页面、游戏、网站、API context 内部入口写到代码就近 `README.md`。
- map 只负责把用户说法路由到这些事实源。

## 最小 Design 范围

如果用户确认本方案，下一 phase 只设计以下改动，不重启旧“三系统 + Agent Entry”方案：

1. 新建 L3 代码拓扑主文档。
2. 修正 L1 / L3 / map 中容易暗示“全面纵向”的摘要和路由。
3. 修正 Case Design 的可执行检查项与“横向铺模块”术语。
4. 更新公开上下文解耦文档。
5. 不新增通用实践经验条目，不改具体业务项目。

## Conclusion

最合适的主位置是 `_adoc/L3-core/ai-friendly-code-topology.md`。它是 AIPD 的长期代码架构判断；Case Design 是执行投影，`docs/modules/context-decoupling.md` 是公开解释，具体项目的 L5 / 局部 README 是实例化结果。
