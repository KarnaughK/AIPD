# Think：产品文档与产品原型设计经验吸收

## 当前问题

AIPD 已有较成熟的代码项目开发经验，但缺少从产品问题、需求文档、信息架构、交互流程到可验证原型的系统指导。用户特别要求流程不能止于 Agent 一次生成，而要强制回看、发现遗漏并迭代后再交付。

## 调研范围

- 高关注度开源 Agent Skill / 方法仓库中的产品设计、UX、UI、原型、PRD、需求澄清和评审流程。
- stars 只作为发现信号；最终看方法完整度、执行约束、反馈闭环、许可证和 AIPD 适配度。
- 区分产品定义 / 交互原型 / 视觉设计 / 前端实现，避免用前端美化 Skill 替代产品设计。

## 不查什么

- 不做泛化的传统产品经理书单或设计工具采购比较。
- 不以单张视觉稿质量作为核心结论。
- 不在 Think 阶段直接实现新 Skill 或复制外部仓库内容。

## 预期输出与停止条件

- 找到一组有明确公开来源和当前采用度证据的候选。
- 深读至少 3 个高相关候选，能够指出其流程节点、产物、迭代 gate、优点和缺口。
- 能形成 AIPD 自己的“发散 -> 原型 -> 多视角评审 -> 修订 -> 验证 -> 收敛”流程骨架，并明确它该落在哪些层。

## 分支

- `open-source-skill-scan/summary.md`：候选检索、证据和吸收判断。

## 回流位置

- 先回到本文件和 `case.md` 的 Think 摘要。
- 用户确认后进入 Design，设计实践经验、Case 条件 gate 和 Goal Mode 回跳语义的最小组合。

## 调研结论

高关注度候选中，没有一个 Skill 单独覆盖从产品问题、产品文档、方案发散、原型实验、状态扫描、可用性验证到经验回流的完整链条。最优方案不是选一个仓库照搬，而是组合其已经被采用和反复实践过的强机制：

- 产品文档：采用 staged co-authoring 与 fresh-reader test，解决作者上下文污染。
- 产品方案：强制至少 3 个结构上不同的方案，先发散再收敛。
- 原型：定义为回答一个问题的可丢弃实验，并记录证据与结论。
- 保真度：用当前最大未知项选择最低必要保真度，不无理由从文字直接跳到高保真 / 代码。
- 评审：产品类交付在 Verify 至少做一次低成本 Reduction Scan；只有命中注意力冲突、内部方法压过用户问题、简化未传播等触发器时才回到 Design。
- 迭代：回跳后必须产生包含删除、合并、延后 / 渐进披露或重排的 Reduction Delta；只有加法不算有效迭代。
- 退出：一次完整扫描不再命中触发器、注意力路径清楚且没有新证据 / 新观察视角时自适应停止，不规定两轮或三轮。
- 治理：流程、参考知识、案例经验、确定性检查和行为 eval 分层维护，避免再次长成万能 Prompt。

详细证据见 `open-source-skill-scan/summary.md`。

## Think 决策

- **选定方向**：不新增一套大型产品设计 Skill 或 SOP。用一条具象 experience 保存案例方法，在 Design 条件命中时写 Attention Contract，在 Verify 对真实产物执行 Reduction Scan；Goal Mode 命中触发器后自主回到 Design，直到自适应收敛。
- **明确不选**：不复制某个高赞聚合仓库的产品设计 Prompt；不把 UI 生成或设计系统检索误认为完整产品设计；不把 simulated review 写成真实用户验证。
- **用户修正**：固定轮数会拖慢普通任务，也可能让 Agent 在错误指标上继续加法；最终采用“固定审视入口、按触发器回跳、按收敛证据停止”。
