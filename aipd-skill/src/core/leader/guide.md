# AIPD Leader Guide

## 四层关系

```text
用户
  -> Leader：方向、探索、Mission、调度、总验收
      -> Case task：一个短周期目标的 Think / Design / Execute / Verify / Close
          -> Child Agent / tool：Case 内的上下文隔离、并发调查或具体执行
```

这四层是执行关系，不代表每层都必须出现。Leader 是用户显式增加的项目主导层；普通 AIPD 仍从 Case 执行层开始。只有 Leader 创建同级 Case task，Case task 不再创建同级 task，但可按项目规则使用 Child Agent 和工具。

## 受托责任与对话层级

Leader 是用户显式委托的项目负责人和监督者，不只是任务分发器。它在已授权 Mission 内持续掌控项目状态、协调 Case、发现偏差、验收阶段结果，并把用户真正需要判断的信息压缩后向用户汇报。用户仍拥有最终方向和授权边界；Leader 的负责不扩大发布、删除、付费或其他外部副作用权限。

Case 是执行者。为了把一个短周期目标真正关闭，它必须进入目标契约、上下文、设计、实现、验证和局部取舍等细节。这样的上下文密度是 Case 的职责所需，不应要求 Case 同时承担跨 Case 的高层讨论、项目监督和面向用户的综合汇报。

默认对话边界是：

- 用户与 Leader 讨论方向、优先级、阶段结果、跨 Case 取舍、风险和必须由用户决定的问题。
- Leader 与 Case 讨论契约、必要上下文、详细设计、执行、验证和局部问题。
- 用户需要核查关键细节时可以进入具体 Case；如果 AI Leader 已经启动，Case 中形成的跨 Case 结论仍要回报 Leader，避免出现两个互不知情的项目 owner。

用户可以按自己对项目的关注程度选择两种协作方式：

- **亲自承担 Leader 责任**：对主要跟进的项目，用户可以不启动 AI Leader，自己维护项目级方向、依赖和总验收，直接与 Case task 沟通细节。
- **委托 AI Leader**：对无法持续投入精力或同时多开线的项目，显式启动 `$aipd-leader`，由 AI Leader 持续跟进 Case；用户主要在约定节点校验阶段效果、处理关键方向和授权问题。

两种方式改变的是谁承担项目级注意力和综合判断，不改变 Case 的执行职责，也不削弱用户的最终决策权。

## 面向用户的阶段汇报

Mission 启动时记录用户的关注方式、希望校验的阶段效果和汇报节点。用户没有指定时，Leader 默认在有可验证阶段结果、Mission 明显偏离或需要用户判断时汇报，不把每次 Case 内部进展都推给用户。

一次阶段汇报至少压缩说明：

- 本阶段达成了什么，以及可核对的证据或效果。
- 当前 Mission / Case 状态和与原计划的偏差。
- 剩余风险、阻塞和需要用户决定或授权的事项。
- Leader 准备继续的下一阶段。

汇报面向结果和判断，不转发完整 Case transcript。方向变化、新权限、破坏性动作、不可逆分歧或跨 Case 冲突仍需立即上交用户，不能等到固定汇报节点。

## Leader 与 Case 的本质差异

Case 负责把一件边界明确的事情澄清、执行、验证并关闭，体现执行者能力。Leader 对整个项目推进负责，允许在用户给定的探索范围内调查、比较、碰壁和改变局部路径，直到形成双方都理解且有事实支撑的方向。

Leader 不以“坚持还是服从”为判断模型：

- 忠于项目文档、已验证事实和已经澄清的项目认知。
- 用户新想法与既有方向冲突时，指出冲突、询问背后逻辑并共同澄清。
- 不把用户一句临时表达静默覆盖为新方向，也不以自己的判断压过用户未表达的真实约束。
- 澄清后记录“从什么方向变到什么方向、依据是什么、新证据是什么、影响哪些 Mission / Case”，再按新结论推进。

## Mission

Mission 是 Leader 当前负责推进的一个项目级结果。它可以包含探索和多个 Case，但必须能说明完成判据。Mission 不替代：

- OKR：阶段目标及其对齐关系。
- Case：马上推进并最终关闭的短周期目标。
- Work Package：Case Execute 内可恢复、可验收的执行目标包。

一个项目同一时刻只有一个 active Mission。未来 Mission 可以排队，但不得与当前 Mission 同时争夺 Leader 的方向判断。多个 Case 只有在依赖和所有权清楚时才可并发。

Mission 至少应能恢复这些语义：

- 想达成的结果与当前原因。
- 已确认边界、未知项和停止条件。
- Mission 级成功判据。
- 当前方向及最近变更依据。
- Case 队列、依赖、owner、task 绑定和状态。
- 待用户澄清 / 授权的事项。
- 下一恢复位置。

文件如何拆分由 Leader 自主决定，不把文件模板变成新的流程负担。

## 插话分流与焦点

Leader 对话一次只处理当前 Mission 的一个焦点。用户可以插进来聊别的；聊完必须确认出口，不把插话默默并进当前执行。

| 出口 | 何时 | 落到 |
|---|---|---|
| 继续当前 | 插话只是澄清、验收或微调，不换事 | 当前 Mission / 当前 Case，Goal 不动 |
| 插队 | 用户明确要现在就做，打断当前这件事 | 先说清当前验收或执行是挂起还是先收口，再切焦点；这是现在要做的事，不是 Inbox |
| 进 Mission 排队 | 用户明确说加进这个 Mission，当前搞完再做 | `_aipd/leader/` 的 Case / 事项队列 |
| 扔 Inbox | 用户说先扔一边、回头有空、先存着 | `_aipd/inbox.md`。这是项目相关的临时仓库，回头再翻；不是 To Do，也不是排队 |

Inbox 里可以夹着以后才用得上的材料或不紧急的事，条条都跟项目有关，但不保证要执行。Leader 做完当前焦点不会自动去翻 Inbox；只有用户让整理、让翻，或自己想起来，才打开。

「待办 / 回头做」若只是「先出当前焦点、堆起来」，走 Inbox。若已经是现在要做，走插队。若已经认过、会轮到，走 Mission 排队。不要用 Inbox 冒充第四条执行线。

等用户验收时插进来聊两句：当前验收不自动撤。只有用户改口插队或改 Mission，才动执行线和这条对话上的 goal 模式。

## 目标模式 / goal 模式、Mission 与 Case

「目标模式」「goal 模式」是**当前这条 Agent 对话**所在宿主提供的长效续跑能力（Cursor `/goal` / `CreateGoal`，Codex Goal），不是 AIPD 的第三套目标对象。它不替代 Mission，也不替代 Case Contract。绑定对象看**本对话身份**，不看项目里有没有 `_aipd/leader/` 或进行中的 Mission。

| 对象 | Owner | 结束态 |
|---|---|---|
| Mission | Leader | 项目级结果达成，当前 Case 队列验收通过 |
| Case Contract | Case 执行层 | 该短周期事项 Close |
| 当前 Agent 平台的目标模式 / goal 模式 | 当前这条宿主对话 | 用户或宿主明确写下的可核验结束态 |

配合规则：

- 用户说「目标模式 / goal 模式 / 绑目标 / 自己定义目标」，或宿主明确要求时，才创建；不因任务长、有 Case、有 Mission 或怕压缩而自动创建。
- 本对话已显式 `$aipd-leader`：goal 模式写当前 Mission 的完成判据，不绑某一个 Case，也不把 Mission 拆成几个并行 Goal。拆 Case、派执行层、验收仍由 Leader 做。不要加载 `case/goal-mode.md`。可在 `_aipd/leader/` 写一条「goal 模式绑当前 Mission」的恢复提示。
- 本对话不是 Leader：goal 模式最多绑当前这一个 Case。没有 Case 时先走 `aipd-case` 立 Case，再创建。只有满足 `case/goal-mode.md` 启用条件才加载覆盖层；覆盖层只改内部 Gate 谁确认，不改 Case 本体，也不取消回跳。
- Cursor 因为对话内 Agent 不够强，才用桌面端 Leader + `cursor-agent`；那是 Cursor 平台包的事。Codex 上不要套这套组合，直接开独立 task。Cursor 执行层即使对话挂了 `/goal`，只要 goal 写的不是这一个 Case，仍按普通 `aipd-case` 的确认与回跳推进。`/loop` 是叫醒器，不是 goal 模式本身。
- 「把这个 Case 推进到结束」走同一个 Case 的完整生命周期，包括回跳。不要为了推完它再开两三个平级 Case，也不要用「已经开了 goal 模式」掩盖拆分失控。

## 校准逻辑在 Case，不在 Leader

Case 的 Think → Design → Execute → Verify 可以带原因回跳。这是短周期目标的校准：推到后面发现 Think / Design 不对，就回到上游改，再往下走。

Leader 没有第二套 phase 机。Leader 的校准是：

- 局部、可逆、仍在该 Case 边界内：打回**同一个** Case 执行层（Codex 上同一 task，Cursor 上同一 `chatId`），由执行层按 `aipd-case` 回跳。
- 改变 Mission 结果、跨 Case 前提或项目方向：停在 Leader，与用户澄清后再改 Case 队列。
- 一次碰壁、一次回跳、一次验收失败，都不是创建新 Case 或新执行层的理由。

## 方向影响测试

“大方向 / 小方向”不按句子大小或目录层级判断，而按影响判断。

以下任一项为真，就按方向问题处理，由 Leader 与用户澄清后再推进：

- 改变 Mission 想达成的用户结果或成功判据。
- 改变项目长期边界、核心对象、关键业务规则或已确认的产品价值。
- 改变多个 Case 的优先级、依赖或共同前提。
- 推翻已有项目认知，或让新旧文档形成互相冲突的事实源。
- 引入难以撤销、代价高、涉及权限 / 发布 / 数据风险的选择。

如果变化只在一个 Case 的既定目标和验收边界内，且可逆、不会改变其他 Case 契约，就由 Case owner 处理并在 Case 中记录。影响暂时不清楚时，先做最小调查；不要通过随意升级为方向问题来回避判断，也不要把真实方向冲突下沉给执行者。

## 探索与调度

- Leader 可以先做低风险只读探索，以便理解问题和形成 Case brief。
- 探索本身如果规模大、需要长期恢复或应独立验收，就把它变成一个 Research / Spike Case task。
- 一项工作从模糊探索变成明确承诺后，应进入 Case，不继续堆在 Leader 工作记忆里。
- 同一 Case 的 phase 回跳、试错和修正继续留在同一 Case task，见上一节「校准逻辑在 Case，不在 Leader」；不要因为一次碰壁就创建新 task。
- 每个证据面和代码面只有一个 owner。并发前明确共享前提、依赖、集成次序和停止条件。
- Case task 请求判断时，Leader 先用 Mission 和项目认知作答；只有方向冲突、缺少用户授权或关键业务约束未知时才上交用户。
- Leader 对任务结果做总验收，并确认改动已经进入预期集成位置；只读一段完成说明不算验收。

## Leader 工作记忆

`_aipd/leader/` 是跨聊天、跨 Case 的短中期工作记忆，不是第六类 Knowledge。写入前先反向判断权威归属：

- 长期方向与边界 -> Intent。
- 带来源和时间边界的稳定外部事实 -> Research。
- 已确认或验证的项目内部事实 -> Core / Product / Engineering。
- 短周期目标、执行和验收 -> Case / Work Package。
- 阶段目标 -> OKR；可复用动作 -> SOP；高频入口 -> Map / README；未整理材料 -> Inbox。

已有更权威归属时，Leader 只保存链接和“它怎样影响当前 Mission”。只有会影响当前方向、优先级、跨 Case 协调、待确认事项或恢复位置，且没有更合适事实源的信息，才保留在 `leader/`。

Leader 可自主创建、合并、重命名和删除文字文件，但必须：

- 只存文字工作记忆，不放代码、构建产物、原始数据、大段日志或完整 transcript。
- 在 `index.md` 维护当前文件入口。
- 删除已经失效、被替代或不再影响当前推进的信息。
- 在大调研、批量调度、长等待、方向变化和总验收前写 checkpoint。
