# AI 友好代码拓扑运行时指南

本指南帮助 Agent 在新增模块、调整文件边界、抽取 shared 或设计跨模块组合时，控制上下文跳转、隐性依赖和改动牵连面。

它是一套边界判断合同，不是固定目录模板，也不要求项目全面纵向化。现有项目的 `_aipd/map.md`、Engineering 知识域、局部 README 和真实代码事实优先；除非用户明确要求，不得因为读取本指南而顺手重构既有拓扑。

## 先区分两个命名空间

| 问题 | 纵向 | 横向 |
|---|---|---|
| 代码拓扑 | 纵向业务上下文 | 横向基座、横向共享能力 |
| AIPD 项目工作区 | 五类并列知识域 | Map、SOP、Case 等独立能力 |

本文只讨论代码拓扑。五类知识域不套用代码拓扑的纵向 / 横向语义；新增多个彼此独立的业务模块称为“并列扩展”，不要把空间上的并列误写成横向共享。

## 核心模型

项目通常同时包含三类模块：

- **横向基座**：多个业务上下文共同需要、但不拥有具体业务需求的技术地基，例如路由、部署、日志、鉴权、数据访问适配、站点壳和稳定页面运行机制。
- **横向共享能力**：已经被多个真实业务上下文使用、语义稳定、输入输出清楚且具有独立 owner / 验证边界的能力。
- **纵向业务上下文**：围绕一个业务目标，把相关输入、规则、状态、输出和局部实现尽量收在有限上下文内的模块。

模块之间通过 **显式组合边界** 连接。它是连接方式，不是第四类模块。

## 纵向业务上下文怎么识别

页面、业务弹框、网站、SEO 页面、游戏、API 业务链路都可能成为纵向业务上下文；文件名和目录层级不能自动决定它。

优先检查：

- 是否围绕一个清楚的业务目标，而不是只按 controller / service / model 等技术职责分类。
- Agent 能否在有限局部上下文内读清输入、规则、状态、输出和验收条件。
- 是否可以独立修改、验证和演进，而不必同时审计大量无关调用方。
- 外部是否只依赖稳定入口，不穿透内部 service、store、私有组件或中间状态。

`纵向` 描述业务归属与演进方向；`黑箱` 描述边界质量。纵向业务上下文应尽量形成黑箱，但横向基座和横向共享能力同样必须有清楚黑箱边界。

## 显式组合怎么判断

允许的组合应满足：

- 调用方只依赖小而稳定的输入、输出、事件或协议。
- 被组合模块拥有自己的状态、规则、生命周期和内部实现。
- 替换被组合模块时，调用方不需要重写业务主干。
- 组合关系可以在 Design、Engineering 知识域、局部 README 或测试中被直接定位和验证。

如果两个模块需要互相知道大量内部细节，先检查边界是否切错；不要继续增加隐式引用或用共享状态把它们粘在一起。

## 共享能力的晋升条件

遵循 `Decouple first, DRY later`：先让能力在纵向业务上下文中独立成立，再观察是否值得沉淀为横向共享能力。

不能仅凭代码相似、调用次数或假想需求抽取 shared。上移前至少确认：

- 已有多个真实使用者。
- 使用者依赖同一稳定语义，而不只是代码形状相似。
- 输入输出小而清楚，不要求调用方理解内部状态。
- 抽取后减少理解跳转和牵连面，而不是制造新的全局依赖网。
- 存在独立 owner、测试或替换边界，变更影响可以验证。

业务语义仍可能分叉、抽取后需要大量模式参数或交叉状态时，可以暂时复制完整局部实现以保护独立演进。复制是阶段性手段，不是永久目标；条件成熟后仍应重新评估共享。

## Brownfield 执行顺序

调整现有项目时按以下顺序判断：

1. 先从项目 map、Engineering 知识域、局部 README 和代码确认当前事实与 owner。
2. 识别本次业务目标属于哪个纵向业务上下文。
3. 列出它允许使用的现有横向基座与横向共享能力。
4. 判断新增引用是稳定组合，还是穿透了其他模块内部。
5. 判断 shared 变化是否满足晋升条件；未获 Design 明确批准时，默认不新增共享层。
6. 只做满足目标所需的最小 delta，不把局部任务扩成全局拓扑重构。
7. 明确当前上下文如何独立验收，以及稳定结果需要写回哪里。

## Case Design 输出：Code Topology Contract

当 Case 会新增或调整模块 / 文件夹边界、shared / domain / utils 上移、跨上下文依赖或组合协议时，Design 应在 Context Boundary 中写一份短的 `Code Topology Contract`：

- **拓扑敏感**：是 / 否。
- **纵向业务上下文**：本次新增或修改哪个业务上下文，由哪些目录 / 文件承载。
- **允许的横向依赖**：可以使用哪些现有基座和共享能力。
- **显式组合边界**：跨上下文通过什么输入输出、事件或协议连接。
- **禁止事项**：哪些跨边界引用、内部穿透或主干回流不允许出现。
- **共享变化权限**：是否允许新增 / 上移 shared；未明确时默认为不允许。
- **独立验收边界**：怎样证明当前上下文可以独立理解、修改和验证。
- **认知回写**：稳定后应更新哪些知识域、局部 README 或 map；代码拓扑规则通常进入 Engineering，但不得把其他知识域的事实强塞进 Engineering。

Design 负责做出这些决定，不能把拓扑选择留给 Execute 临场发挥。

## Execute 与 Verify 的合同

- 拓扑敏感的 Work Package 必须携带与本包有关的 `代码拓扑护栏`，Execute 开始前先做 preflight。
- Execute 默认执行项目具体合同，不重新解释整套通用指南；如果实现需要改变上下文、依赖方向、组合接口或 shared 权限，应停止相关变化并回到 Design。
- Verify 应对照真实 diff、目录、依赖关系、测试和文档回写检查合同，而不只检查代码能否运行。
- 设计仍成立但实现偏离时回 Execute；事实证明合同本身不成立时回 Design。

## 认知落点

- 当前 Case 的采用方案：Design Context Boundary / Design Summary。
- 已实现且跨多个代码入口的工程规则：目标项目 `_aipd/knowledge/engineering/`。
- 页面、API、游戏、网站等模块内部入口：代码就近 `README.md`。
- 高频自然语言到认知 / 代码入口的路由：目标项目 `_aipd/map.md`。

通用指南只帮助做判断，不能替代目标项目自己的事实源。

## 非目标

- 不提供跨技术栈统一目录模板。
- 不规定页面、API、组件或网站天然就是纵向上下文。
- 不用文件长度、token 数、重复次数或调用数量自动决定拆分与共享。
- 不为了形式上的纵向纯度拒绝已经成立的横向基座或共享能力。
- 不预建没有真实使用面的巨大平台。
- 不把代码拓扑的纵横术语套到 AIPD 知识与流程系统，反之亦然。
