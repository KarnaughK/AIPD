# 教学文档产品化与用户旅程组织

## 来源

- 来源类型：AIPD 开源项目 README 与学习文档的一次完整改造。
- 真实范围：审计已演进的 Skill 和运行模型，参考 Vue、React、Django / Diátaxis、Rust 和 Next.js 的文档分工，改写根 README、学习入口、6 章连续课程和 11 篇能力说明。
- 验证方式：检查本地链接、Skill 集合、脚本路径、过时语义、构建产物一致性，并人工走查“快速体验、连续学习、工作时查阅”三条路径。
- 经验性质：文档产品实践经验，不是固定目录模板，也不是通用 API 文档规范。

## 适用场景

在 Think / Design 阶段，当任务涉及以下任一情况时，应读取本经验：

- 为开源项目新写或大幅重写 README、入门文档、学习路径或教程。
- 项目功能和组织架构已多次演进，但文档仍沿用旧分类、旧概念或旧命令。
- 文档单页都“有内容”，但新读者仍不知道为什么要用、第一步做什么、怎样得到第一个有意义的结果。
- 团队准备把多个对象说明串起来当教程，或把底层系统架构直接当作用户学习顺序。

小范围拼写修正、单个 API 参数补充、纯内部代码注释，不需要套用整套方法。

## 核心判断：稳定的是用户任务，不是当前组织架构

Skill、模块、对象名、目录和产品架构都会变。如果教学文档按当前系统对象排队，每次架构变化都会迫使读者重建学习路径。

更稳定的锚点是读者需要完成的工作：

1. 判断这个项目是否和自己有关。
2. 建立一个足以开始行动的心智模型。
3. 完成第一个有意义、可验证的结果。
4. 在实际工作中查到具体对象、规则和边界。
5. 遇到偏差时知道如何恢复、排错或继续深入。

因此，“按用户旅程组织教学，按系统对象组织参考”是这条经验最耐变化的部分。AI 能力、交互方式或项目组织改变时，可以换掉具体页面和对象，但仍然先重新确认这五类用户任务。

## 已验证的文档分工

本次实践中，三层分工有效：

| 层级 | 主要任务 | 读者离开时应得到什么 |
|---|---|---|
| 根 README | 决策页 | 知道项目解决什么、是否适合自己、怎样最快看到价值、下一站去哪里 |
| guide / tutorial | 连续课程 | 被带着完成一个真实结果，并在行动中逐步建立心智模型 |
| modules / explanation / reference | 解释与查阅 | 在工作时快速找到某个对象的定义、边界、用法、故障处理和相关入口 |

这些是页面职责，不是必须照搬的目录名。小项目可以合并页面，大项目可以建立文档站；只要每个入口的主要任务清楚，同一套逻辑仍然成立。

## 从审计到交付的方法

### 1. 先建立“当前事实包”

不要直接润色旧文案。先对照源码、命令、配置、目录和当前工作流，列出：

- 已成熟、可对外承诺的能力。
- 已更名、已迁移或已废弃的概念。
- 只是试验、规划或目前不支持的边界。
- 从安装到第一个可见结果真正需要的操作。

这一步的目的是防止“文案更好看，但产品事实更不准”。

### 2. 定义读者和第一个成功时刻

明确主要读者已经知道什么、正在解决什么、为什么会离开。然后定义一个最低但真实的成功结果。

成功时刻不应只是“安装完成”或“读完所有概念”，而应是读者已经完成一件和项目价值直接相关的事。

### 3. 调研方法，不复制表面

调研其他项目时，关注它们如何完成读者分流、第一次成功、渐进披露、教程与参考分工，不要照搬首页模块、四宫格或目录命名。

参考项目的交互能力、用户前提和产品形态不同时，应找到自己的低摩擦替代。例如无法提供交互式沙箱时，可以用真实目录、可执行命令和可验收结果承接“边学边做”。

### 4. 选择一条因果旅程

教学主线应表达“为什么下一步是这一步”，而不只是把模块 A、B、C 排成线性目录。

AIPD 这次改造使用的具体旅程是：

```text
任务前：找到正确认知
  -> 任务中：让目标和状态留在文件里
  -> 任务后：把稳定经验留给下一次
```

这条旅程不是通用答案。可迁移的部分是：用读者看得见的因果链串起概念，并让每一章产生一个更接近真实成功的结果。

### 5. 给每个页面一个主要工作

先写页面职责，再写正文。对每个页面至少回答：

- 读者什么时候进来？
- 他带着什么问题？
- 离开时应该知道什么或完成什么？
- 这个页面有哪些信息应该链接到别处，而不是在此展开？

一个页面可以兼顾次要任务，但不应同时对“完全新手”和“正在排查细节的熟练用户”展开同等深度。

### 6. 允许必要重复，防止定义漂移

一句话心智模型、核心循环和必要前提，可以在 README、课程和参考页面局部重复，以保证深链接进入时仍然能理解。

容易变化的完整对象列表、字段、脚本细节和平台差异，应由参考层或源码附近的事实入口维护，首页和教程通过链接引用。

## 常见失败路径

### 用系统分类冒充用户旅程

文档按内部模块排列很完整，却无法回答读者为什么应该从模块 A 读到模块 B。系统分类适合参考层，不自动等于教学顺序。

### 把“快速开始”停在安装成功

安装只是前置条件。如果读者在第一个价值时刻前仍需要自己猜测命令、数据和操作顺序，快速开始就没有完成任务。

### 把对象字典串成所谓课程

每篇都回答“它是什么、有什么属性”，但没有连续场景、决策和结果。这类内容可作为参考文档，不应冒充首次学习路径。

### 为了吸引而超出当前事实

把规划中、试验性或只在某个平台成立的能力写成通用承诺，短期可能更吸引人，长期会让教程无法复现，并且损害信任。

### 只检查 Markdown，不走读者路径

链接全部存在不等于读者知道该点哪里。语法和链接检查只能验证文件，还需要人工从首次入口走到第一个成功时刻，再从工作中的具体问题走到参考页面。

## Verify 检查面

文档产品的验收至少包含五个面：

### 事实准确性

- 能力名、数量、命令、参数、路径和平台边界与当前源码一致。
- 旧概念只出现在迁移说明或历史背景中，不作为当前规则。

### 可到达性

- 本地链接、锚点、示例文件和脚本路径真实存在。
- 保留必要的稳定路径，避免重写文档后旧深链接全部失效。

### 旅程完整性

- 从首页能在少量决策内进入快速体验或完整学习。
- 连续课程不依赖读者先查完全部参考页。
- 第一个成功时刻可见、可执行、可验证。

### 独立入口可理解性

- 参考页可以从搜索或深链接直接进入，开头说明何时需要它及它在整体旅程中的位置。
- 页面不依赖只有顺序阅读才能理解的隐性上下文。

### 可维护性

- 完整对象列表和易变事实有清楚的维护主入口，而不是在多个教程中各复制一份。
- 用户任务没有变时，优先更新参考事实和中间操作，不因内部重构轻易推翻整条教学旅程。

## 架构或 AI 能力变化时如何更新

当 Skill、Agent、组织架构或 AI 操作方式发生变化时，不要默认从新的系统目录重建教程。先问：

1. 读者的目标和第一个成功时刻变了吗？
2. 用户可见的因果链变了吗？
3. 只是内部对象、执行者或文件归属变了吗？

如果前两项没变，保留用户旅程，更新具体操作和参考事实即可。只有当用户目标、价值时刻或可见因果链真正改变时，才需要重设教学主线。

## 不做

- 不把三层分工当作所有项目必须采用的文件树。
- 不用教程替代 API / Reference；它们服务不同用户任务。
- 不因为文档要吸引人，就省略前提、限制、安装副作用和尚未成熟的能力边界。
- 不把外部优秀项目的页面结构当成品质证明，也不照搬它们的文案、导航和交互规模。
- 不只验收文件格式；必须验收读者是否能完成目标。
