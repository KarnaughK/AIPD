# 产品设计注意力编排与触发式减法

这条经验来自一次真实的 AI 产品原型协作：目标是做一个“活着的 AI 图鉴”。Agent 能持续执行、能完成多条路由和详情页，也会主动补证据、补状态、补解释；但它把“完整、丰富、差异化”当成了主要质量指标，结果首页尚清楚，详情页却逐步长成约 8 屏、9 个区块的长页面。用户要求列表简化后，简化只发生在列表页，没有传播到同一产品的详情页。

问题不在于 Agent 没有迭代，而在于它围绕错误指标迭代。固定要求“再做两轮”只会让错误方向继续变完整；有效机制应当固定审视入口，按触发条件决定是否推翻，并允许删除已经完成的设计。

## 什么时候读取

在以下 Case 中读取本经验：

- 产品文档、PRD、产品原型、用户流程、信息架构或用户可见页面是主要交付物。
- 用户提出“太多、太复杂、再简化、重点不清、像文档搬上网页”。
- Agent 将在 Goal Mode 下自主完成产品类 Case，用户不会逐轮监督。
- 列表、详情、同类页面或多条路径容易各自膨胀，需要让同一产品判断跨页面传播。

普通代码修复、纯后端改造和不涉及用户注意力的文档维护不触发这套机制。

## 失败模式

### 1. 用完成度代替产品判断

路由数量、字段覆盖、证据数量、组件数量、构建通过和响应式完整都可以被验证，但它们不能回答用户第一眼应该看见什么。Agent 容易继续增加内容，因为“增加”比“决定什么不出现”更容易证明工作量。

### 2. 自审只有加法，没有推翻权

如果自审的隐含问题是“还缺什么”，每轮都会补卡片、补解释、补状态。真正的产品自审必须同时允许删除、合并、延后、隐藏和重排；当前设计只是暂定解，不是需要保护的沉没成本。

### 3. 用户纠偏只修当前页面

“太复杂”通常不是一个组件级 bug，而是产品判断发生了变化。若只改用户点名的页面，后续页面会按旧指标重新膨胀。纠偏必须明确传播范围：当前区块、同类页面、整条用户路径或整个产品。

### 4. 验证工程正确，却不验证注意力

build、测试、路由、响应式和可访问性通过，只说明产物能运行。产品类 Case 还必须对真实产物做一次首屏 / 前十秒审视，检查信息竞争和用户下一步，而不是只复读 Design 文档。

## Design：先写注意力契约

产品类 Case 在 Frontend / UX / State Design 中增加一份短的 Attention Contract。它不是完整 UX 流程，只回答：

- **用户时刻**：用户此刻带着什么问题来到这里？
- **主问题 / 主动作**：这个页面只允许哪一个问题或动作占据最高优先级？
- **注意力路径**：第一眼看到什么 -> 随后理解什么 -> 自然采取什么动作？
- **信息层级**：哪些是 `now`、`next`、`on-demand`、`remove`？
- **传播范围**：这条判断只适用于当前页面，还是同类页面 / 整条路径？
- **自我推翻权限**：在不改变 Case Contract 的前提下，Agent 可以删除、合并、隐藏、延后或重排什么？
- **触发条件**：出现哪些可观察现象时必须回到 Design？
- **停止条件**：什么证据足以说明继续迭代只会产生 churn？

信息优先级不能只看频率。至少同时看：

- 当前场景相关性。
- 对决策是否必要。
- 后果与紧迫性。
- 是否可逆。
- 使用频率。

低频但不可逆、后果严重的信息可能必须前置；高频但可预测的信息可以压缩。少即是多不是减少底层事实，而是减少同一时刻互相竞争的内容；完整事实可以留在数据源、证据层或渐进披露中。

## Verify：触发式减法循环

产品类交付在进入 Close 前，至少执行一次低成本 Reduction Scan。检查真实截图、原型、可运行页面或最终文档，不根据计划稿想象结果。

### 触发器

命中任一项，就说明当前设计仍需回到 Design：

- 同一视口或同一阅读段有两个以上同等醒目的主重点。
- 无法用一句话说清用户第一眼看什么、下一步做什么。
- 某段内容出现的主要理由是“显得完整”，而不是支持当前用户问题。
- 低相关或低决策价值信息压过当前关键内容。
- 页面主要在解释内部分类、证据系统或实现模型，而不是回答用户问题。
- 用户已经表达“太多 / 太复杂 / 简化”，但同类页面或后续路径仍按旧密度继续扩张。
- 本轮只有新增字段、卡片、解释或状态，没有删除、合并、延后、隐藏或重排。

### 回跳记录

Verify 命中触发器时，写明：

- 触发器和真实证据。
- 回到哪个 Design artifact。
- 影响当前页面、同类页面还是完整路径。
- 哪些既有设计 / work package 暂时失效。

Design 修正后必须形成 `Reduction Delta`：

- **delete**：删掉什么。
- **merge**：合并什么。
- **defer / disclose**：延后或按需展示什么。
- **reorder**：重新安排什么。
- **outcome**：为什么这会让用户更快完成当前目标。

只有加法的轮次不算有效的 Reduction Delta。若新的证据表明确有必要增加内容，必须同时说明它替代、压缩或降级了什么，或者明确记录这是 Case Contract 要求的例外。

### 自主修改边界

Agent 可以在 Case Contract 内自主推翻：

- 信息层级、分组、顺序和默认展开状态。
- 页面区块、视觉权重、渐进披露和文案密度。
- 已完成但没有继续存在价值的局部设计与实现。

Agent 不得静默改变：

- 产品目标、目标用户、角色和权限。
- 业务规则、数据真实性要求和验收标准。
- Case 范围、不可逆决策或需要用户独有判断的取舍。

越过后一组边界时，按 Case / Goal Mode 的暂停规则询问用户，而不是借“简化”改写目标。

## 自适应停止，而不是固定轮数

不规定两轮或三轮。每次回跳必须由新的证据、触发器或观察视角驱动，并产生可见的 Reduction Delta。

满足以下条件即可停止：

- 一次完整 Reduction Scan 没有命中触发器。
- 主问题和“看见 -> 理解 -> 行动”路径清楚。
- 非当前信息已经被删除、降级或渐进披露。
- 用户先前的简化偏好已传播到声明的页面族 / 用户路径。
- 再做一轮没有新证据或新观察视角，只会重复同一判断。

停止的依据是收敛，不是 Token 消耗、执行时长、页面数量或预设轮数。

## Case 中的落点

```text
Design
  -> Attention Contract（条件命中）
Execute
  -> 产出真实页面 / 原型 / 文档
Verify
  -> Reduction Scan
      -> 未触发：继续 Close
      -> 已触发：记录证据，回到 Design
Design
  -> Reduction Delta + 传播范围
Execute
  -> 修正受影响产物
Verify
  -> 再扫描，直到自适应收敛
```

Goal Mode 下这是一组内部质量 Gate。只要没有越过目标、范围、业务规则、权限或外部副作用边界，Agent 应自主回跳并继续推进，不把每一轮内部审视变成用户审批。

## 具象校准

在 AI 图鉴详情页里，“家族 ≠ 系列 ≠ 版本”可能是正确的内部数据建模规则，但它不一定是用户进入某个模型详情页时的首要问题。更合适的注意力路径可能是：

```text
先认出这是什么、适合谁
-> 快速理解核心能力和限制
-> 选择继续了解、比较或使用
-> 需要时再展开版本关系、证据和来源
```

底层信息没有丢失，只是从“全部同时出现”变成“在用户需要时出现”。这正是产品减法与数据完整性的边界。
