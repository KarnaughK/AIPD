# 高级模型设计 + 执行模型写代码：一次完整流程记录

## 来源

- 来源：raprap.tv 项目 Case `c2-emd-generation`（2026-11-16）。用户口述要求按原样记录整个操作流程，下次让 Agent 通读后照做。
- 结果：Opus 5.5 写设计；Grok（`grok-4.7-build-fast`）在后台把 7 个工作包按顺序全部做完，用时约 80 分钟，中途没有停下。自动检查全部通过，Grok 审查没有阻塞问题。用户手动验收还没做完，本条之后可能补充。
- 经验性质：流程记录，不是抽象规则。下面写的是这次实际怎么做的，换项目时按实际情况改。

## 什么时候读

- 用户说“你设计、让 Grok 干活”“省 Opus 额度”“高级模型配便宜模型”，或者有类似分工要求。
- Case 进入 Design 阶段，而代码量明显大到不该由高级模型自己写。

## 为什么这样分工

- 用户的约束：Opus 额度少，Grok 额度多。用户只在乎 Opus 用了多少 token。
- Opus 用多少 token，主要看调用了几次工具，而不是输出了多少字。每次调用工具，整段对话都要重新读一遍。对话到了 15 万 token 时，自己写代码要调用工具 80–120 次。交给 Grok 写，自己只做设计加最后验收，只需要 10–15 次。
- 所以要守住三件事：只派一次活；执行期间不查进度；验收放到新对话里做，新对话只读几份 Case 文件。
- 这次审查发现的 3 个小问题，全部出在设计里，Grok 照设计写的部分没有出错。可见瓶颈在设计，高级模型的额度应该花在设计上。

## 整体时间线（这次实际发生的）

1. 用户提出需求（EMD 页的生成链路、弹框登录、素材和作品管理）。Opus 先读项目 `_aipd/map.md` 和相关代码，用讨论格式答复“缺什么”。这一步不改文件。
2. 用户确认开新 Case，并明确了分工：Opus 设计，Grok 执行；设计要细到“较弱的模型照着做、不用自己想”。
3. Opus 补读设计需要的代码细节，一共调用约 40 次工具：数据库事务在 D1 上是空壳、Nitro 定时任务在 Cloudflare 上可用、better-auth 有匿名登录插件、本地 R2 没配置等。
   - 教训：这一步用户等了十几分钟，又看不到进度，会不安。**补读期间每隔几次调用就用中文说一句在干什么。** 发现会影响方向的事实，先跟用户商量再继续。
4. Opus 写 Case 和设计文档，分几次写，每写完一份报一次进度。
5. 用户审阅，修改暂定值。Opus 按用户意见改文档里的常量。
6. 用户问：“让 Grok 干活，再由你验收，会不会比你自己干还费 token？”Opus 给出估算（见上文），并提出“Grok 一次做完 + 新对话验收”。用户同意。
7. Opus 写工作包、执行说明、审查说明和启动脚本。先用一次小测试确认 `grok -p` 在没有界面时也能调用工具，然后在后台启动。只抽查一次 Grok 读了哪些文件，确认没有越界，之后这个对话就停下。
8. 约 80 分钟后用户回来问“干完了没”。Opus 只读进度表、自动检查日志和审查报告（共约 10KB），就汇报结果，并请用户手动点一遍。

## 设计文档要写到什么程度

这次的设计文档在 raprap.tv 仓库：`_aipd/case/archive/c2-emd-generation/02-design/`。下次要写设计，**先通读这几份当样板**，不要凭这里的摘要重新编。

| 文件 | 内容 | 大小 |
|---|---|---|
| `design.md` | 一句话设计、流程图、已确认 / 暂定值 / 关键决策三张表、复杂点和解法、工作包规划、**执行 Agent 通用规则**、Readiness Gate、后续候选 | 约 10KB |
| `backend-design.md` | 常量；环境变量；每张表逐字段写清（TS 名 / 列名 / 类型 / 约束 / 索引，三种数据库写法）；状态机表；每个函数的签名和逐步行为；每个接口的入参、返回、错误码和 HTTP 状态；端到端脚本逐步写清 | 约 41KB |
| `frontend-design.md` | 每个组件的文件位置、对外接口、状态表、每个状态的显示和行为、i18n key（中英文都写好）、验收步骤 | 约 18KB |
| `context-boundary.md` | 代码拓扑合同（允许依赖什么、禁止什么、哪些共享代码可以动）；**每个工作包一张“允许改动的文件”表**；开发环境现状（数据库、端口、哪些没配、基线报错数、哪些用户改动不能碰） | 约 7KB |
| `decision-log.md` | 决策、原因、来源 | 1KB |

具体到什么程度，看这几条就知道：

- 函数写到签名加步骤，例如“先查幂等键 → 查到就返回 → 查有没有配生成服务 → 统计进行中单数 → 开事务插入行并扣积分 → 撞唯一约束就再查一次 → 事务后同步推进一次”。
- 错误写到错误码对应 HTTP 状态，例如 `insufficient_credits` → 402，并且 data 带 `{ required, balance }`。
- 可以复制的现成代码，直接写“从 X 文件复制 Y 函数，不要 import”，避免执行 Agent 为了复用去改别人的模块。
- 每个工作包都写出验收命令，可以直接复制运行：tsc、test、具体 curl 和期望的状态码、grep 检查有没有越界引用。
- 不确定的地方明确写“暂定”，并告诉执行 Agent 遇到时怎么办，例如“Hotel Lobby 价格先填 1 占位，文件顶部写 TODO”。
- 有明确的停止规则：设计没写到、又会影响字段 / 接口 / 状态 / 积分的情况，执行 Agent 不自己发明，标 blocked。只影响内部实现细节的，按最简单的做法做，并写进“偏离设计”。

设计阶段读代码时，要核对“会让设计变成错的”那类事实，而不是把功能先实现一遍。这次核对的有：模板的事务在 D1 上是空壳（所以设计不依赖事务正确性）；Nitro 定时任务能不能打包进 Cloudflare 产物；better-auth 客户端怎么刷新登录状态；本地 R2 和生成服务的 key 都没配（所以加了本地测试模式）；tsc 和 test 的基线。

## 执行层文件（全部在 `_aipd/case/archive/c2-emd-generation/03-execute/`）

下次**直接复制这几份改路径和内容**：

| 文件 | 作用 |
|---|---|
| `grok-brief.md` | 执行说明。每个工作包都先读它 |
| `grok-review-brief.md` | 审查说明。最后一个独立 Grok 只读它和代码 |
| `run-grok.sh` | 启动脚本 |
| `execute.md` | 执行方式、**验收入口**（给新对话的 Opus 看的读取顺序）、进度表 |
| `work-packages/wp-NN-*.md` | 每个工作包一份 |

### 执行说明里必须有的话（这次的原文要点）

- “你是子 Agent。只做指定的那一个工作包，做完就结束。”
- “仓库根 `AGENTS.md` 里的 AIPD 流程（项目状态 gate、map 检索、Case 推进、回复格式、Leader、goal 模式）对你不适用。不要创建子 Agent，不要改 `case.md` 和 `02-design/`。”
  - **一定要写。** 否则执行 Agent 会被仓库的 AGENTS.md 带去走 AIPD 流程。
- 必读顺序：design.md 的关键决策和通用规则 → 自己的工作包 → 工作包列出的设计章节 → context-boundary 里自己的那张文件表 → 工作包列出的参考代码。“不要大范围扫描仓库。”
- “不要读或打印 `.env.*`（`.env.example` 除外）、数据库里的数据行（看表结构可以）、`_aipd/` 下本 Case 以外的目录。”
- 不要 git add / commit / push / stash / reset / checkout / restore；不要停止或重启用户的开发服务。
- `db:push` 如果要求交互确认，或者要做新建表 / 新建索引以外的变更：不确认、不加 `--force`，直接标 blocked。
- 前序工作包有 bug 挡住自己时，只做最小修复，并在“偏离设计”里写明。
- 完成时：逐条跑验收并打勾；填执行记录；**状态行只能写成 `**状态**：completed` 或 `**状态**：blocked`（全角冒号，脚本靠这一行判断）**；tsc 或 test 没过就不能写 completed；在 `execute.md` 进度表追加一行；最终回复只写一行。

### 工作包模板（这次每个包的结构）

```text
# Work Package: wp-NN - 名字
> 所属 Case / 类型 / 执行: Grok / 依赖 / 拓扑敏感
## 目标            一两句话
## 设计依据        指向 backend/frontend 的具体小节，写“这是唯一依据”
## 允许改动的文件  指向 context-boundary 第 2 节的那张表
## 参考代码（只读） 列 3–5 个真实文件，并说明看它的哪一部分
## 验收标准        [ ] tsc 只剩基线 N 条；[ ] test 全过；[ ] 具体 curl/grep/sqlite 命令 + 期望结果
## 不做            本包容易越界做的事
## 执行记录        **状态**：pending / 改动文件 / 验证结果 / 偏离设计 / 未解决问题
```

### 启动脚本要点（`run-grok.sh`）

```bash
GROK=(grok -m grok-4.7-build-fast --reasoning-effort xhigh --always-approve --no-plan --cwd "$ROOT" --output-format streaming-json)
for WP in wp-01-... wp-02-... ...; do            # 按依赖顺序串行
  done_wp "$FILE" && continue                     # 已 completed 的跳过 → 脚本可重跑
  note "$WP" started ...                          # 往 execute.md 进度表追加一行
  "${GROK[@]}" -p "你是…执行 Agent。先完整阅读并遵守 grok-brief.md，然后只执行工作包 $FILE。" > "$LOGDIR/$WP.log" 2>&1
  done_wp "$FILE" || { note ... STOPPED; echo C2_RUN_STATUS=stopped >> execute.md; osascript 通知; exit 1; }
done
# 自动检查：tsc 报错数、pnpm test、e2e 脚本、pnpm build、产物 grep、git status → 04-verify/auto-checks.log
# 独立 Grok 审查：读 grok-review-brief.md → 写 04-verify/grok-review.md
echo C2_RUN_STATUS=finished >> execute.md; osascript 通知
```

- 每个工作包开一个**全新的 Grok 会话**，避免上下文越积越多。
- 判断一个工作包是否完成，**只看工作包文件里的状态行**，不解析 Grok 的输出。
- 启动：`nohup bash run-grok.sh > /tmp/.../runner.log 2>&1 & disown`。日志放在 `/tmp/raprap-c2-grok/`。
- 启动前先做一次小测试：`grok ... -p "run: echo ok > /tmp/x"`，确认无界面模式下能调用工具。这次 11 秒通过。
- 这次没给单个工作包设超时，属于已知风险。

### 为什么串行，不并行

设计里原本按批次规划了并行（A 批三个包同时做）。实际执行改成串行，原因是：同时运行的 Agent 会抢 `pnpm build`、i18n JSON 和 schema；串行时每个包都能看到前一个包的成果；总时间 80 分钟可以接受。

## 审查与验收

- **自动检查**由脚本完成：tsc 报错数和基线对比、单元测试、不用起服务的端到端脚本、构建、产物里有没有定时任务、git status。
- **独立审查**再开一个 Grok，只写一个文件，按优先级检查：积分（重复扣、重复退、扣了没退、没扣就生成）→ 状态机（UPDATE 有没有带状态条件、租约是否在 finally 释放）→ 安全（鉴权、归属、密钥比较、路径穿越、生产环境是否关掉假服务、postMessage 是否校验 origin、内部错误有没有泄露）→ 代码拓扑（用 grep 查禁止的 import）→ 签名是否和设计一致 → 有没有改到文件归属表之外的文件（列出用户原有改动作为豁免）。
- 输出格式：第一行写总结论，然后是问题表（阻塞 / 重要 / 建议）和逐项“已检查无问题”的列表。
- **验收入口**写在 `execute.md`，给新对话的 Opus 用：
  1. 进度表末尾的状态；
  2. auto-checks.log；
  3. grok-review.md；
  4. 只亲自读一个最关键的文件（这次是积分和状态机的 `service.ts`）；
  5. 其它代码只在审查报告指出问题时才读；
  6. 返工写成修复工作包，用同一个脚本交给 Grok；
  7. 请用户手动点一遍。

## 和用户沟通时要注意的

- 用户看不到 Agent 在干什么时会焦虑。长时间读代码时，每隔几次调用就给一句中文进度；遇到意外情况先商量。
- 价格、上限、超时这类业务常量，用户会直接改（这次并发上限 2 → 10；“退款”的意思是退积分，不是退钱）。设计里集中放在常量表，改起来只动一行。
- 用户问“这样会不会更费 token”时，给按数量级的估算表，并说清楚哪几种做法会让它变得更费：反复查进度、逐行读代码、自己动手返工。
- 派出去之后告诉用户三件事：怎么看进度（进度表、`tail -f` 日志）、跑完会弹通知、回来开新对话说“继续 cN，验收”。

## 执行模型额度用尽时（2026-11-17 实际遇到）

- 一个月内可用模型会变：`grok-4.7-build-fast` 从账号里消失，只剩 `grok-4.7`。启动前先跑 `grok models`，脚本里的 `-m` 用当前可用的。模型不存在时 grok 立刻退出，日志里是 `unknown model id`。
- 额度用尽时，日志末尾是 `You’ve reached your free Grok Build usage limit`，工作包状态停在 pending。**不要直接重做**：先跑自动检查、用 grep 对照验收标准。这次 Grok 在用尽前已经把代码写完，只差填执行记录，Main 核对后补记录即可。
- 确实没写完时，换用 `cursor-agent`（本机已登录），同一份执行说明和工作包不用改。

## 本次的坑

- 审查发现的 3 条建议都是设计没写细：释放租约时没带自己的令牌；幂等查找没排除已软删的行；submit 等待期间没有推迟下一次轮询时间。下次写状态机时直接把这三点写进设计。
- 工作区里有用户和其它 Case 的未提交改动。审查说明里要列出豁免路径，否则会被报成越界。
- 设计里写了并行批次，执行改成了串行，但设计文件没有同步改。下次直接在设计里写“串行”。
