# Think：AIPD Update 版本模型

## 问题

当前 `aipd-update` 把“符合最新 Schema 规则”当成运行前提。项目一旦缺少最新文件或规则，它更容易停止并报告问题，而不是完成升级；同时 Skill 自己复制了一整套最新结构规则，容易和 AIPD 当前文档再次分叉。

## 用户确认的模型

设目标项目已应用版本为 P，本机安装的完整 AIPD 版本为 I：

1. 从本机版本目录中选择 `(P, I]` 的全部更新记录。
2. 这些记录只用于理解这段时间发生了什么、为什么变化、哪些判断已被后续版本覆盖，以及哪些项目定制需要保护。
3. 读完记录后，再读取版本 I 随包提供的当前文档、模板和运行规则，它们才是最终态事实源。
4. 再读取目标项目的真实状态和项目定制。
5. 由 AI 一次性把项目收敛到 I，不依次把 V6、V7、V8、V9 的中间形态写进项目。
6. 验证成功后，最后写入项目已应用版本，并追加一条简短项目更新日志。

## 关键反例

项目从 V5 升到 V9，V6 到 V9 可能反复修改同一个规则：先改出去、再撤回、又换方向。逐版执行会制造无效改动和额外风险；正确做法是理解这段演进，再直接落到 V9 当前定义。

## 边界

- “最新”只指本机已安装 AIPD 的 I，不指 GitHub 或网络上的 R。
- 即使远端已有 V12，只要本机 Skill、版本目录和当前文档一致处于 V9，Update 就只负责 P -> V9。
- 远端发现、下载和提醒属于未来能力，本 Case 不做。
- 当前完整 Schema v2 成为第一版正式版本化基线；不伪造此前逐版历史。

## 决策出口

- **Create**：进入 Design / Execute，建立版本事实源并重写 `aipd-update`。
- **停止条件**：无法保证本机版本目录、当前文档和打包产物属于同一个完整快照；或发现版本状态不可判定、项目版本超前、破坏性冲突需要用户决策。
