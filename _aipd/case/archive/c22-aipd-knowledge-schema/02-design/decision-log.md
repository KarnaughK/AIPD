# Decision Log

## D1：工作区命名

- **决定**：项目级容器使用 `_aipd/`。
- **原因**：该容器同时拥有知识、Map、SOP、Case、OKR 和 Inbox；`_adoc` 无法准确表达整体职责。

## D2：长期知识归组

- **决定**：使用 `_aipd/knowledge/{intent,research,core,product,engineering}`。
- **原因**：共同前缀应成为父目录；语义目录比编号更能表达并列分类并支持未来扩展。

## D3：逻辑标识与物理路径

- **决定**：物理路径使用目录层次；逻辑类型使用 `knowledge.intent` 等点式标识。
- **原因**：点号适合命名空间，不适合承担物理目录分组；下划线前缀会重复父级语义。

## D4：Engineering 命名

- **决定**：原 Dev 域改为 Engineering。
- **原因**：该域存的是产品到代码之间的跨模块工程逻辑，不是具体代码或日常开发过程。

## D5：兼容策略

- **决定**：不提供运行时兼容，只提供一次性迁移器。
- **原因**：双读和 fallback 会长期保留两套事实源；一次性迁移器是升级工具，不属于运行时架构。

## D6：检索 Agent 命名

- **决定**：`aipd_adoc_retriever` 改为 `aipd_context_retriever`。
- **原因**：它输出的是当前任务上下文包，检索范围除了五类 Knowledge，还包括 SOP、必要流程状态、局部 README 和代码入口；`knowledge` 会把职责说窄。

## D7：遗留目录哨兵

- **决定**：新运行时发现仅有 `_adoc/` 时拒绝初始化并提示运行一次性迁移器。
- **原因**：直接当成未初始化会生成第二套工作区；拒绝性检测不读取旧内容，因此不是运行时兼容。
