- **当前阶段**：整体方向和工作空间边界已设计，首站仍在 Think，尚未完成网站实现。

## Branch Goal

记录 Page One 如何以网站 / 域名作为纵向盒子，以公共平台、观测和跨站增长能力作为横向候选，并明确哪些只是规划、哪些已经写入项目事实。当前不把它推广为 AIPD 通用架构。

## 项目目标与生产方式

用户从历史 SEO 关键词中寻找尚未被满足的明确需求，再围绕关键词：

1. 注册或选择一个匹配需求的域名。
2. 建设一个精致的单页面网站，直接满足该关键词背后的功能需求。
3. 上线后持续观察流量、来源和真实使用反馈。
4. 根据反馈决定继续投入、调整或停止。

一个域名可以匹配一个或多个相关关键词需求；一个域名对应一个独立网站。

## 规模增长特征

- 单站预计可以在三到四天左右完成。
- 一个月可能新增四到五个网站。
- 两个月可能增长到十余个网站。
- 工作空间会持续新增彼此独立的域名项目，而不是把所有关键词工具堆进同一个网站。
- 网站上线并不代表工作结束，还要承接流量监测、来源分析和后续运营判断。

## 已设计的工作空间边界

用户描述的目标结构：

```text
PageOne/
├── platform/        # 多站点公共底层和管理能力
├── <domain-a>/      # 一个域名、一个独立网站
├── <domain-b>/      # 一个域名、一个独立网站
└── ...
```

当前仓库事实：

- `PageOne/` 已存在 AIPD 项目认知、根 README 和 `platform/README.md`。
- 当前只有 `platform/`，尚未创建真实域名网站目录。
- 首站候选 `glitch text generator` 已创建 Case，但仍停在 Think，尚未产生网站代码。
- 因此，本案例记录的是“已经明确落盘的架构约定 + 尚未实现的能力规划”，不是成熟运行结果。

## 纵向维度：一个网站一个盒子

- 每个域名目录代表一个独立网站。
- 每个网站拥有自己的需求、关键词上下文、产品认知、代码和基础设施映射。
- 网站不读取其他网站的内部上下文，也不因同属 Page One 就混成一个公开工具门户。
- 单个网站通常只是一个功能聚焦、内部复杂度有限的精致单页面，适合作为独立纵向盒子。
- 如果某个网站内部后来产生额外复杂度，可以像案例 01 的页面 / 组件一样，再划分更小的纵向模块。

用户认为这种纵向划分主要服务关键词上下文窗口：Agent 进入某个站点时，只需要理解这个域名对应的关键词、用户需求、页面和验证目标。

## 横向维度：多站点公共底层

用户当前设想或仓库已确认的横向候选包括：

### 观测与后台管理

- 多网站统一埋点。
- 流量、来源和使用数据汇总。
- 公共的数据查看或后台管理能力。
- Cloudflare、Supabase、GitHub 等跨站服务接入与自动化。

`platform/README.md` 已把这些内容列为公共底层职责，但具体技术栈和实现仍未确定。

### 通用业务与技术能力

- 真正具有跨网站复用价值的业务类代码。
- 前端技术类公共能力。
- 多站共用的脚本、组件和基础服务。
- 公共能力按真实需求逐步沉淀，不为未来可能复用而预建完整平台。

### 跨站展示与引流能力

用户提出的规划候选：

- 统一的网站侧边栏、标题或醒目引流区。
- 单页面网站可以在视觉上呈现多个导航入口。
- 当前站点自身只承载一个核心功能；其他导航按钮统一跳转到一个大型 AI 主站。
- 大量细分 SEO 站点既独立满足搜索需求，也可能成为 AI 主站的流量入口。

这部分目前是增长架构设想，尚未在 Page One 仓库中形成实现或稳定规则。

## 公共层当前明确不负责什么

Page One 已有文档明确：

- `platform/` 不承载单个网站的产品需求和页面实现。
- 不把网站之间本应隔离的业务上下文集中到公共层。
- 不为复用而提前建设通用建站平台。
- 公共底层只承接已经出现或即将被真实使用的跨站需求。

## 用户对纵横关系的当前观察

用户原先强调纵向，是为了让一个网站对应一个关键词需求上下文，使网站可以独立生产、理解、上线和验证。

但当网站数量持续增长后，项目不可避免地出现跨站需求：数据观测、后台管理、服务接入、公共组件、自动化以及站群到 AI 主站的引流。因此 Page One 从设计之初就需要同时保留：

```text
横向公共底层 / 多站点能力
              ↓
纵向独立域名网站
```

这仍是案例内观察，尚未与其他案例合并成通用结论。

## 当前未决问题

- 公共业务代码、前端技术代码和真正的平台基础设施应如何区分，尚未设计。
- 统一侧边栏、标题和导航最终通过共享包、模板生成、复制还是运行时服务接入，尚未决定。
- 大型 AI 主站的具体身份、导航策略和站群引流边界尚未定义。
- 统一埋点、数据汇总和后台管理使用什么数据模型与技术栈，尚未决定。
- 每个站点是否完全独立部署、如何共享升级、失败站点如何下线，等待真实站点实践。
- 首站 `glitch text generator` 尚未通过 Think Gate，因此还没有实际验证纵横结构。
