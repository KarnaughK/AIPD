## Branch Goal

记录 Guessword.io 如何在一个主题域名内部，同时形成页面与游戏两类纵向盒子，并由页面嵌入游戏；再区分跨页面 / 跨游戏的横向底层。当前只保存案例事实、方向和未决边界，不推广为 AIPD 通用架构。

## 项目目标的变化

用户最初希望围绕域名及“猜单词”主题，争取同名的大型 SEO 关键词，但这个关键词本身竞争难度较高。

后续方向不再只依赖一个大词和一个游戏，而是：

1. 锁定“猜单词”这一稳定主题。
2. 在同一网站内逐步建设多种猜单词小游戏。
3. 让喜欢猜单词的用户可以持续发现和游玩不同玩法。
4. 用与具体游戏相关的长尾 SEO 页面承接搜索需求，并让用户在页面内直接试玩对应游戏。

因此，`guessword.io` 的潜在产品边界不是“一个关键词对应一个单页面”，而是“一个主题域名容纳多个相关游戏和多个搜索入口”。

## 页面与游戏的组合结构

用户描述的目标关系可以暂记为：

```text
Guessword.io
├── 页面上下文
│   ├── 直接游玩页 / 游戏主体页
│   └── 面向具体 SEO 关键词的文章页
├── 游戏模块
│   ├── 当前语义相似度猜词
│   └── 后续其他猜单词玩法
└── 跨页面 / 跨游戏的公共底层
```

页面不是游戏核心本身，而是游戏的承载和分发入口。一个页面负责自己的搜索意图、标题、内容和展示结构，并在合适位置嵌入一个游戏模块。

## 纵向盒子一：游戏模块

- 每一种猜单词玩法都应形成一个完整的游戏模块。
- 游戏模块拥有自己的玩法规则、状态、交互、展示和必要的业务上下文。
- 不同游戏模块之间不直接读取或调用彼此的内部实现。
- Agent 开发、修改或优化某个游戏时，主要加载该游戏模块的上下文即可。
- 即使多个游戏表面上拥有相似元素，也不应仅为消除重复就让它们共享内部状态和玩法逻辑。

游戏模块是否包含自己的后端 API、数据模型、埋点事件和运营读模型，目前还没有在本次案例中定死；用户当前明确的是游戏核心应作为纵向黑盒。

## 纵向盒子二：具体页面

用户当前提到两种页面形态：

### 直接游玩页 / 游戏主体页

- 页面可以不承担一个额外的长尾 SEO 关键词。
- 页面注意力主要放在游戏本身，让用户直接开始游玩。
- 它仍可以看作承载游戏模块的一种页面模板，而不一定需要成为独立于“模板页”的架构类别。

### SEO 文章页

- 页面针对一个与某款游戏相关的具体 SEO 关键词。
- 页面独立优化 title、正文内容和搜索意图。
- 页面内嵌入一块可直接游玩的游戏区域，而不是只写文章或只跳转到别处。
- 不同 SEO 页面拥有不同关键词上下文，页面之间也尽量保持纵向独立。

这里暂时保留一个术语缺口：如果“模板”指可被很多页面复用的渲染骨架，它更接近横向能力；如果“模板页”指一个拥有具体关键词、内容和组合关系的实际页面，它就是纵向页面盒子。两者不能在后续分析中混为同一个对象。

## 页面与游戏之间的边界

该案例不是要求页面和游戏完全不发生关系，而是把关系收窄为组合：

- 页面决定为什么展示这个游戏，以及围绕什么关键词和内容展示。
- 游戏模块决定游戏内部如何运行。
- 页面通过稳定入口嵌入游戏，不读取游戏内部状态管理和实现细节。
- 同一个游戏模块未来可能被一个直接游玩页和多个 SEO 文章页承载。

“页面如何传入配置、游戏如何回传事件、是否允许一个页面组合多个游戏”仍是待设计接口，不在采集阶段预设。

## 横向维度：公共页面与技术底层

用户本次只明确指出页面之下仍会存在横向底层。结合 Guessword.io 当前项目事实，可观察到的横向候选包括：

- 路由、布局、语言和基础页面壳。
- metadata、canonical、hreflang、sitemap、robots 等 SEO 基础设施。
- 通用标题、页头、页尾、导航和样式基础。
- 匿名访问、埋点、反馈和流量观测能力。
- 游戏模块被页面嵌入时需要遵守的稳定接口。
- 部署、Cloudflare 资源和其他真正跨模块使用的技术能力。

这些候选并不表示所有代码都必须集中共享。当前 Guessword.io 文档也明确要求：产品局部行为先留在自己的纵向 context，只有真实跨 context 需求出现后才上移。

## 当前仓库事实与未来方向的时间边界

当前 Guessword.io 已经提供了一部分相关证据，但还不是目标拓扑的完整实现：

- 项目长期定位已经允许一个域名承载多种猜词玩法。
- 当前阶段明确暂不扩展更多游戏，先做深语义相似度猜词、内容质量和复玩体验。
- 当前产品认知已区分 SEO 静态内容与动态游戏区的职责。
- ShipAny Next 首页由 `[locale]/page.guess.tsx` 渲染 `[locale]/_game/GuesswordApp`。
- `[locale]/_game/` 已被项目定义为页面局部的纵向游戏 context，不应为了通用化而移入 ShipAny 公共模块。
- 当前 `/games-like-semantle` 已是一张独立 SEO 内容页，但它目前通过 CTA 跳回首页游戏，并没有把游戏模块直接嵌入文章页。
- ShipAny 的账号、支付、CMS 和后台等横向能力仍在源码树中，但当前 Guessword Worker 没有启用这些路由。

所以，本案例同时包含：

1. 已落地的“单个页面入口 + 单个纵向游戏 context + 横向运行底座”。
2. 尚待验证的“多个页面盒子组合多个独立游戏模块”的主题站架构。

## 用户对纵横关系的当前观察

在同一个主题网站内部，纵向单元不只存在于一个层级：具体页面可以是纵向盒子，具体游戏也可以是纵向盒子；两者通过清晰的嵌入关系组合。横向底层则服务多个页面或多个游戏，但不承载它们各自的关键词内容和玩法内部状态。

这可以作为本案例对“有纵有横”结构的证据，但当前仍不与案例 01、案例 02 合并，也不据此形成通用规则。

## 当前未决问题

- “游戏主体页”最终是独立页面类型，还是页面模板的一种实例。
- “模板”究竟指共享渲染骨架，还是指每一张具有具体 SEO 意图的页面；后续需要拆词。
- 一个游戏是否会对应多个 SEO 页面，以及页面与游戏的路由映射方式。
- 游戏纵向盒子是否同时拥有前端、API、数据和运营上下文。
- 页面嵌入游戏时的最小稳定接口是什么。
- 不同游戏之间哪些 UI 或技术能力有资格进入横向共享层。
- 多游戏方向何时结束“暂不扩展”的当前阶段，尚未形成执行决策。
