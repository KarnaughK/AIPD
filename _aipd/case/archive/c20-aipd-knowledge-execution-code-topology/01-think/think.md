# c20 Think：真实项目案例采集

## 当前问题

AIPD 对 AI 友好代码拓扑的判断不应从抽象术语直接出发。先按时间顺序保存真实项目中的结构和取舍，等案例齐备后再比较：

- 哪些能力横向复用。
- 哪些业务单元纵向内聚。
- 什么情况下复制优于共享。
- 项目类型和技术栈如何改变边界。
- 早期实践与后续认知如何演进。

## 采集边界

- 当前只收集用户亲历项目。
- 一个项目一个 Think 分支。
- 先记录事实、当时理由和结果，不统一术语，不评价对错。
- 只有影响事实准确性的歧义才追问。
- 用户明确“案例讲完了 / 可以分析了”后，才开始跨案例比较。

## 暂存观察，不是结论

- 案例 01 显示：AIPD 最早的纯前端实践并非真正“全面纵向”，而是已有横向通用框架与纵向页面 / 组件共同存在。
- 案例 02 显示：Page One 在规划阶段已把独立域名网站作为纵向盒子，并把多站观测、管理、服务接入和增长能力留给横向公共底层。
- 案例 03 显示：Guessword.io 在一个主题域名内部，可以把具体页面与具体游戏分别视为纵向盒子，由页面通过稳定边界组合游戏，并保留跨页面 / 跨游戏的横向底层。
- 跨案例共同支持的方向是：横向基座与后置形成的横向共享能力，承托可独立理解、修改和验收的纵向业务上下文；纵向上下文可以嵌套或通过稳定边界组合。
- 该结论仍是探索性决策模型，不是固定目录规范；案例 02 和案例 03 的未实现部分不能包装成已验证实践。
- 术语上应以“并列扩展”替代“横向铺模块”，避免和横向基座 / 横向共享能力混淆。
